# e2e-mobile CI job: from a 6h hang to a trustworthy green run

## Problem

The `e2e-mobile` GitHub Actions job (`.github/workflows/ci.yml:96-244`) runs the Maestro visual/accessibility flows in `maestro-flows/visual/` against a real Android emulator, on every PR. Getting this job to a genuine, trustworthy green run took nine cascading fixes over several hours on 2026-09-01, all on this same job. Each fix uncovered a new, previously-hidden failure underneath it — a missing backend, then a missing user, then a stale hardcoded database id, then an OS-level dialog obscuring a correctly-rendered screen, then a third-party action's own broken cleanup step. None of these were visible until the layer above it was fixed, which is what made this a multi-hour investigation rather than a single fix.

This job builds on prior work (session history, PR #9, 2026-08-22 to 2026-08-29) that first got the Maestro flow files themselves correct — fixing a mismatched `appId`, ambiguous text selectors, keyboard occlusion, and adopting a project-wide convention of asserting on `testID` rather than visible text specifically because EN/FR i18n makes text selectors unreliable. That work is documented separately (see Related Issues below); this doc picks up once the flows were correct and the focus shifted to getting the *CI job itself* to run them trustworthily.

## Symptoms

In the order they were encountered:

1. The CI run sat `in_progress` for 6 hours before GitHub's own job-level time cap force-cancelled it (runs `33502440934`/`33412573855`, referenced in `ci.yml:105-107`) — not a clean pass or fail, and invisible while running because GitHub does not surface live logs for an in-progress job.
2. After adding `timeout-minutes: 25` (`ci.yml:108`) to get faster signal, Maestro immediately failed with `Flow path does not exist: .../frontend/maestro-flows/visual`, and separately the job still silently hung to its new timeout cap on that same failure.
3. After fixing the path issue, 2 of 3 Maestro flows failed with `AxiosError: Network Error` on `POST /auth/login`. App logs showed `Frontend API Base URL: http://10.0.2.2:4000/api` (the Android emulator's alias for the runner's own localhost) — nothing was listening on port 4000 (`ci.yml:119-124` documents this as run `33506976320`).
4. After adding a real backend service (`ci.yml:110-118`, `172-181`), login returned a legitimate `401 AUTH_FAILED` ("Invalid email or password") instead of a network error — progress, but still a failure.
5. After seeding a user via signup, the `expense-list-screen` flow failed with `Element not found` / assertion failures once it tried to interact with a specific group.
6. After building full API-driven fixtures (user + group + expense, `ci.yml:182-207`), all 3 flows failed on an early assertion like `Assertion is false: id: email-input is visible`, timing out after only 13-24 seconds — well under Maestro's own 60s flow-level `testTimeout`, meaning it was Maestro's per-element wait timeout, not the whole-flow timeout.
7. Downloading the actual Maestro debug artifact (`gh run download <run-id> -n maestro-debug-output`, matching the upload step at `ci.yml:236-241`) and viewing the failure screenshots — not just the assertion text — revealed the real cause: a literal Android system dialog, "Pixel Launcher isn't responding," sitting on top of a correctly-rendered login screen (run `33512863222`, cited in each flow file's header comment, e.g. `maestro-flows/visual/login-screen.yaml:7-11`).
8. Even after adding a dismiss tap for that dialog, a second run's screenshots (run `33518292719`, cited in `login-screen.yaml:21-25`, `group-list-screen.yaml:21-25`, `expense-list-screen.yaml:25-29`, and `ci.yml:212-220`) showed the same dialog recurring later in the same flow — proven by the email-input field showing an active focus/blue border in the later screenshot, meaning the flow had progressed past the first dismiss before the dialog reappeared. This was sustained, recurring resource starvation, not a one-time startup hiccup.
9. After a CPU/GPU-load mitigation on the emulator itself (`ci.yml:221-224`), 3/3 Maestro flows passed consistently across multiple runs, but the GitHub Actions job still reported overall conclusion `failure`, because the `reactivecircus/android-emulator-runner` action's own "Terminate Emulator" cleanup step hung on `ERROR | stop: Not implemented` after its own `adb emu kill` succeeded (run `33520968296`, `ci.yml:225-230`) — reproduced even with zero orphaned processes left behind and all tests passing.
10. **(2026-09-02)** A later run (`33534417700`) — on a commit that changed only a comment, no functional change — hit `3/3 Flows Failed` again: the same ANR dialog, but recurring at a point (between the `email-input` and `password-input` assertions in `login-screen.yaml`) that none of the existing dismiss taps covered. Confirmed via screenshot, not assumed. This proved the CPU/GPU mitigation from symptom 9 reduces the flake rate but doesn't eliminate it — it's genuinely probabilistic resource contention on a shared CI runner, not a fixed set of dialog-appearance points that can be fully enumerated and instrumented.
11. **(2026-09-22)** Symptom 9's fix bounded the hang's cost (a fixed 18-minute delay per occurrence) but never actually solved the underlying problem it described: the job's own overall conclusion was still, structurally, whatever the hanging `reactivecircus/android-emulator-runner@v2` step's own conclusion was. Multiple consecutive real runs (`33502440934`/`33506976320`/`33510026360`/`33520968296`/`33524592934`) on master reported `failure` with "3/3 Flows Passed" sitting right there in the same log — proving solution point 9's own prevention advice ("document that explicitly... so future readers check the actual test output rather than just the job badge") doesn't scale: it puts the burden on every future human reviewer to remember to distrust the badge, forever, rather than fixing the badge.

## What Didn't Work

- **Assuming the emulator-runner's multi-line `script: |` block behaves like one shell script.** It doesn't: `reactivecircus/android-emulator-runner` runs each line of `script` as its own independent `sh -c` subprocess (`ci.yml:198-206` documents this from inspecting the action's source). This silently broke `cd ..` (no effect on the next line), a captured background PID (`METRO_PID=$!` on one line was empty in the next line's fresh shell), and consequently `kill "$METRO_PID"` (killed nothing, in the wrong shell) — this was the actual cause of the 6-hour hang in symptom 1, since the orphaned Metro process was never reachable to kill and lingered until GitHub's own cap force-cancelled the job.
- **A first attempt to fix the missing-user problem with a bare ad hoc `curl -X POST .../auth/signup` call directly in the workflow.** This technically let the user log in, but was called out as not the "industry standard" approach — it duplicated what should be a proper fixture-building step and did nothing about the deeper problem: `expense-list-screen.yaml` still hardcoded `tapOn: { id: "group-card-9" }`, a raw Postgres autoincrement primary key copied from a real dev database (see the `testID={`group-card-${item.id}`}` pattern at `frontend/src/screens/HomeScreen.tsx:327`). A fresh CI database's first-ever group could never reliably be id 9, so that flow was structurally broken regardless of the user-seeding fix.
- **Assuming the `email-input is visible` timeout failures meant slow app rendering under resource contention, and reaching for "bump the Maestro timeout" as the fix.** Downloading and actually looking at the failure screenshot disproved this immediately — the screen was rendering fine, just obscured by an unrelated OS dialog. A blind timeout bump would not have fixed anything, since the element genuinely never becomes visible while the dialog sits on top of it.
- **Assuming a single `tapOn: { text: "Wait", optional: true }` right after `launchApp` was sufficient to handle the ANR dialog**, based on the first screenshot alone. A second run's screenshots proved the dialog recurred mid-flow, not just at launch, so a single dismiss point wasn't a complete fix by itself — it's necessary defense-in-depth, but the CPU/GPU root cause still needed addressing directly (this is why each flow file ended up with the dismiss tap placed at more than one point — see `login-screen.yaml:12-14` and `26-28`, `group-list-screen.yaml:13-15` and `26-28`, `expense-list-screen.yaml:17-19` and `30-32`).
- **Killing the emulator manually inside the script's own `trap`, before the action's own "Terminate Emulator" step runs** (`ci.yml:231-238`), on the theory — inspired by upstream issue `reactivecircus/android-emulator-runner#381` about an orphaned `crashpad_handler` subprocess on macOS — that the action's hang might be about waiting on a still-alive subprocess. Verified via the run's actual log timestamps (run `33524592934`) that this manual `adb emu kill` call hit the identical `stop: Not implemented` error itself, and the action's subsequent "Terminate Emulator" step still hung afterward against an emulator that was already dead. This proved the hang is unconditional and entirely inside the action's own post-kill code, unreachable from the workflow's own script. The attempt was reverted, with the finding kept as an inline comment (`ci.yml:231-238`) so it isn't retried.
- **(session history) Manually repeating `adb screencap` + reading each screenshot as an image during earlier flow-authoring work** was flagged in a prior session as expensive; that session's takeaway was to prefer reading Maestro's own JSON artifacts (screen-hierarchy dumps) as text where possible. This session's breakthrough (symptom 7) went the other way deliberately — the specific question ("is something visually obscuring an otherwise-correct screen?") needed the actual pixels, which a hierarchy dump would not show as unambiguously. Both are valid depending on the question being asked.
- **(2026-09-02) Assuming symptom 9's CPU/GPU mitigation had fully solved the ANR, since the two runs immediately after it passed clean.** Two consecutive clean runs is weak evidence against a probabilistic flake — the third run (symptom 10) failed the same way, just at a different point in the flow. The mitigation is real and worth keeping (it changed the *rate*), but "it passed a couple of times" isn't proof a resource-contention-driven flake is gone; only a retry-tolerant test invocation, or enough runs to build real statistical confidence, would show that.
- **(2026-09-22) Locally reproducing the exact teardown hang.** Booted the same AVD (`expense-manager-test`) on a local macOS machine and ran a bare `adb -s emulator-5554 emu kill` — it returned in ~2 seconds every time. The hang could not be reproduced locally. This is expected, not a dead end: the hang lives in the Action's own Node.js post-hook behavior on a Linux GitHub Actions runner specifically, not in `adb emu kill` itself — confirming this ruled out chasing a local fix and pointed straight at wrapping the step's own conclusion instead (see solution point 11).
- **(2026-09-22) Upstream community workarounds** from the same `reactivecircus/android-emulator-runner#385` issue thread already cited in symptom 9 (pinning specific API levels, `force-avd-creation: true`, killing `crashpad_handler` directly, switching to `macos-latest` runners) were all reported as unreliable by various commenters in that same thread and were not adopted this round either.

## Solution

Layered on in this order, all in `.github/workflows/ci.yml` and `maestro-flows/visual/*.yaml`:

1. **Collapse the emulator-runner's `script:` into one physical line** using the YAML folded scalar `script: >` (`ci.yml:239-247`), so the whole block runs as a single `sh -c` invocation and state (background PIDs, `cd`, `trap`) actually persists across the script.
2. **Use `set -m` (job control) before backgrounding Metro**, so `kill -- -"$METRO_PID"` (negative PID targets the process group) reaches the bundler/worker children Metro spawns, not just its direct launcher process; also explicitly stop the Gradle daemon (`./android/gradlew --stop`) in the same `trap ... EXIT` (`ci.yml:240-241`), so nothing orphaned survives the script.
3. **Add `timeout-minutes` at both the job level (`ci.yml:108`, 25 minutes) and the emulator-runner step level (`ci.yml:210`, 18 minutes, tighter than the job's)**, so any future hang — the workflow's own or a dependency's — fails fast with visible partial logs instead of silently consuming hours.
4. **Add a real Postgres service plus backend startup** (`ci.yml:110-118` for the service, `172-181` for `npx prisma migrate deploy` → `npm run dev &` → `npx wait-on tcp:4000`), mirroring the pattern already used in the `backend-test` job, so the app under test has a real backend to talk to.
5. **Build E2E fixtures (QA user, named group, named expense) through the real public API** rather than direct DB writes (`ci.yml:182-207`): `POST /api/auth/signup`, then authenticated `POST /api/groups`, then authenticated `POST /api/expenses`. This is required because `backend/prisma/seed.ts:55-57` deliberately skips user creation ("Skip user seeding - let user create accounts via signup") — a fresh CI database has no users at all until fixtures create one through the same interface a real signup would use.
6. **Fix the flow file to stop depending on a database-generated primary key**: `maestro-flows/visual/expense-list-screen.yaml:41-42` now taps `tapOn: { text: "QA Test Group" }` — the group's own rendered name (`<Text ... testID="group-name-${item.id}">{item.name}</Text>` per the pattern at `frontend/src/screens/HomeScreen.tsx:331-337`) — instead of the old `group-card-9` testID that embedded an autoincrement id copied from a real dev database.
7. **Add `optional: true` dismiss taps for the ANR dialog** at each point where it was observed, both right after `launchApp` and again immediately before the step where it recurred mid-flow: `login-screen.yaml:12-14,26-28`, `group-list-screen.yaml:13-15,26-28`, `expense-list-screen.yaml:17-19,30-32`. This uses Maestro's documented no-op-if-absent `optional: true` behavior for transient system dialogs.
8. **Address the ANR's actual root cause — CPU/GPU contention on the runner** — via `disable-animations: true` and `emulator-options: -no-window -gpu swiftshader_indirect -no-audio -no-boot-anim -camera-back none -no-snapshot` on the `reactivecircus/android-emulator-runner` step (`ci.yml:222-224`), reducing background rendering/audio overhead so the emulator's launcher process stops ANRing under load.
9. ~~Accept and document, rather than keep chasing, the remaining unresolved upstream bug in the action's own emulator-shutdown code — matching open issue `reactivecircus/android-emulator-runner#385` (`ci.yml:225-230`) — bounded to a fixed, small cost via the 18-minute step-level timeout, with the actual Maestro test result (3/3 flows passed) documented as the real signal to check in the logs rather than the job's own pass/fail badge.~~ **Superseded 2026-09-22 by solution point 11 below** — bounding the cost of the hang was never the same as fixing the badge, and symptom 11 shows real reviewers didn't reliably keep checking logs over the badge.
10. **(2026-09-02) Retry the whole `maestro test` invocation up to 3x** (`ci.yml:295-302`, wrapped in a subshell so its exit code correctly propagates through the `&&` chain) rather than trying to instrument every possible ANR-appearance point with a dismiss tap. A real app regression fails the same way on every attempt; a transient system dialog won't reliably recur at the same point three times running — this is the standard mitigation for genuinely probabilistic CI/emulator flakiness. Each attempt costs ~1.5min, so 3 attempts still comfortably fit the 18-minute step timeout alongside the ~9-minute build. Also corrected the job's own header comment (`ci.yml:94-107`), which previously recommended adding this job as a required branch-protection check — given symptom 9's confirmed-permanent upstream bug, doing that would block every future PR whenever it fires, regardless of whether the code under test is broken.
11. **(2026-09-22, PR #78, merge pending as of this writing) Decouple the job's conclusion from the hanging step, instead of just bounding the hang's cost.** On the `reactivecircus/android-emulator-runner@v2` step: added `continue-on-error: true` alongside the existing `timeout-minutes: 18` — this forces that step's `conclusion` to `success` regardless of its real `outcome`, so a hung teardown can no longer fail the job by itself. Its inline script's very last action, before control returns to the Action's own hanging teardown, captures the real build+Maestro exit code to an absolute-path file:
   ```
   (for i in 1 2 3; do maestro test ../maestro-flows/visual/ && exit 0; echo "Maestro attempt $i failed, retrying..."; done; exit 1);
   code=$?;
   echo "$code" > "$GITHUB_WORKSPACE/maestro-result.txt";
   exit "$code"
   ```
   A new step immediately after, `if: always()` with **no** `continue-on-error`, is what the job's real conclusion now derives from:
   ```yaml
   - name: Report Maestro test result (source of truth for this job's conclusion)
     if: always()
     run: |
       if [ ! -f "$GITHUB_WORKSPACE/maestro-result.txt" ]; then
         echo "maestro-result.txt not found - the build/Maestro step did not complete (crashed or was cancelled before writing its result), not a teardown hang. Failing the job."
         exit 1
       fi
       RESULT=$(cat "$GITHUB_WORKSPACE/maestro-result.txt")
       echo "Captured Maestro/build exit code: $RESULT"
       [[ "$RESULT" =~ ^[0-9]+$ ]] || { echo "maestro-result.txt contained a non-numeric value: '$RESULT' - treating as failure"; exit 1; }
       exit "$RESULT"
   ```
   A missing file means the build/Maestro step never reached the line that writes it (crashed or was cancelled) — treated as a genuine failure, since a teardown hang only happens *after* a normal script exit. Non-numeric content (a `SIGKILL` truncating the file mid-write during a timeout) is also treated as failure, with a clear message instead of a cryptic bash error. The existing "Upload Maestro debug artifacts on failure" step (`if: failure()`) still fires correctly, because GitHub's `failure()` evaluates a step's `conclusion` — the neutralized `continue-on-error` step's conclusion is `success`, but the new Report step's conclusion is genuinely `failure` when the real result is a failure.

## Why This Works

- **A third-party GitHub Action's own script-execution semantics can differ from a native `run:` step's single-shell-script behavior, and that difference is invisible until something depending on shared shell state breaks.** `reactivecircus/android-emulator-runner` parses and runs each line of its `script:` input as an independent `sh -c` subprocess; collapsing to one folded-scalar line (`ci.yml:239-247`) makes background PIDs, `cd`, and `trap` behave the way they would in an ordinary shell script, because they now genuinely execute in one.
- **An E2E fixture's test data should be provable and reproducible through the same interface real users use.** Building fixtures via `POST /api/auth/signup` → `/api/groups` → `/api/expenses` (`ci.yml:182-207`) exercises the same validation and business logic a real user's request would hit, rather than a parallel, potentially-drifting path (direct DB writes or ad hoc duplicated hashing logic).
- **Test assertions should bind to content a user would actually see, not infrastructure implementation details that vary across environments.** A database primary key (`group-card-9`) is an artifact of whichever database happened to generate it; a group's own name (`"QA Test Group"`) is stable business content that exists identically in any environment that ran the same fixture step. This is the same underlying principle behind the project's existing `testID` convention (session history: adopted project-wide because EN/FR i18n makes raw text selectors unreliable) — bind assertions to something stable, not to an incidental implementation detail.
- **A failure screenshot is ground truth in a way assertion text alone is not.** "Element X not visible" is a symptom with multiple possible causes — didn't render, is present but obscured, or rendered off-screen — and only the actual pixels (the downloaded Maestro debug artifact, `ci.yml:236-241`) distinguish which one actually happened. That's what disproved the "just bump the timeout" theory in symptom 6/7.
- **Some CI flakiness is upstream and outside your control.** The professional response, once the underlying action's own cleanup bug (`#385`) is confirmed unconditional and unreachable from the workflow's own script, is to bound its cost with a tight step-level timeout and document it clearly (`ci.yml:225-230`) — so a red job badge doesn't get misread as "the tests failed" when the actual test output (3/3 passed) says otherwise. **(2026-09-22 addendum: this was necessary but not sufficient — real reviewers kept hitting the misleading red badge anyway, see symptom 11.)**
- **(2026-09-22) `continue-on-error: true` neutralizes a step's `conclusion` for the job's overall status without touching its `outcome`** — so a downstream `if: failure()` that needs the *real* result must key off a different, undecorated step, not the neutralized one. Capturing the real exit code to disk *before* the hanging teardown code path can even run works because the hang only occurs in code that executes after a step's main script exits (the Action's automatic post-hook) — nothing after the file write in that script is ever reachable by the hang.
- **(2026-09-22) Every failure path was traced adversarially (two review passes) before trusting this mechanism**, not just the happy path: an early genuine build failure mid-`&&`-chain is still captured correctly (no stray `||` swallows it before `code=$?` runs); a `SIGKILL` truncating the result-file write during a timeout was checked *empirically* — `bash -c 'RESULT=""; exit "$RESULT"'` and the non-numeric variant both produce bash's own exit code 255, a failure, never a silent success — so even a corrupted file fails closed, consistent with this project's OWASP A10:2025 "exceptional conditions fail closed" standard. One review pass also caught and corrected an inaccurate comment that implied the step-level `timeout-minutes: 18` specifically bounds the teardown hang — composite/JS-action post-hooks run as separate synthetic steps not necessarily bound by the originating step's own timeout, and no cited run had actually isolated whether the step-level or job-level (25min) cap fires first; the comment was reworded to say so is unconfirmed rather than settled fact.

## Prevention

- Before relying on a third-party GitHub Action's `script:` (or similarly-shaped multi-line) input behaving like a native `run:` step, check its actual source or documentation for how it splits and executes that input — don't assume shared shell state carries across lines.
- When a background process is needed inside a CI script step, use `set -m` and kill by process group (`kill -- -"$PID"`), not by the single PID captured with `$!` for the direct child — real toolchains (bundlers, Gradle daemons, etc.) usually spawn children of their own that a bare `kill "$PID"` won't reach.
- Build E2E fixtures through the real API, not one-off ad hoc scripts or direct DB writes, and never let a test assertion couple to a database-generated primary key — assert on business-meaningful, user-visible content instead (a name, a label) so the same flow works unchanged against any freshly seeded environment.
- When a UI assertion fails with "element not visible" in CI, especially against an emulator or simulator, pull the actual failure screenshot or artifact before theorizing about timing or rendering — don't guess from assertion text alone; it can't distinguish "didn't render" from "rendered but obscured."
- Give any external CI dependency (emulators, hosted browsers, third-party actions) a step-level timeout tighter than the job-level timeout, so a hang — whether in your own script or a dependency's internals — fails fast with diagnosable partial logs instead of silently consuming the full budget.
- When a CI job's overall red/green status can be affected by known third-party infrastructure flakiness unrelated to the code under test (e.g. `reactivecircus/android-emulator-runner#385`, open with no merged fix as of this writing), document that explicitly in the workflow file so future readers check the actual test output rather than just the job badge. **(2026-09-22: this alone is not enough — see the next bullet for the preferred fix.)**
- **(2026-09-22) When a CI step wraps a third-party Action with a known-unreliable teardown/cleanup hook, don't let that hook's outcome own the job's conclusion.** Use `continue-on-error: true` on the wrapping step and derive the job's real pass/fail from a value your own script captures plus a *separate, undecorated* step that reports it — the teardown hang then becomes structurally irrelevant to the job's status, not something every reviewer has to remember to distrust. See solution point 11.
- **(2026-09-22) Verify "fail closed" empirically for any shell-based result-passing mechanism in CI**, don't assume it — actually running `bash -c 'RESULT=""; exit "$RESULT"'` and a non-numeric variant to confirm both produce a nonzero exit is cheap and turns an assumption into a checked fact. Do this whenever a step's pass/fail depends on parsing a file that could be truncated by a `SIGKILL`/timeout mid-write.
- **(2026-09-22) Don't flip a previously-excluded job to a required branch-protection check on the same day its reliability fix ships.** Wait for the fix to be observed reliably reflecting real pass/fail over several real CI runs first — as of this writing PR #78 has not yet been confirmed merged or observed on repeated real runs, a genuine open limitation, not yet a proven-in-production result.
- Don't confirm a flakiness fix on a couple of clean runs alone. For genuinely probabilistic (resource-contention-driven) flakiness, prefer a retry-tolerant test invocation over trying to enumerate and instrument every point the flake could occur — a real regression still fails every attempt, so retries don't hide genuine bugs.
- Never mark a job that can fail from known, unrelated infrastructure flakiness as a required branch-protection check without first fixing or fully bounding that flakiness — a permanently-red-sometimes required check blocks merges for reasons that have nothing to do with the code being merged.
